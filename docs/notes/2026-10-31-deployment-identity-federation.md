# Deployment identity for Azure Pipelines using workload identity federation

## What I built
A dedicated Entra application and service principal for the Azure DevOps service
connection, created in the shared Terraform stack. It holds Website Contributor
and Reader on the dev resource group, and a federated credential that trusts one
specific service connection. No client secret exists for this identity.

## Why it exists
The deployment pipeline needs to publish to the web app. A secret held in Azure
DevOps would be a long-lived credential that can be copied, leaked or forgotten.
Federation replaces it with a short-lived token that Azure DevOps requests for
each run, and that Entra accepts only from the configured issuer and subject.
The identity is separate from the Terraform plan and apply identities, so a
deployment pipeline cannot change infrastructure.

## How it works
- The application registration and service principal are defined in
  `azdo_deploy_identity.tf`, with the client identifier exposed as an output.
- The federated credential specifies the Azure DevOps issuer for the
  organisation, the audience `api://AzureADTokenExchange` and a subject that
  identifies one service connection in one project.
- The service connection in Azure DevOps uses the workload identity federation
  option with an existing identity. It was created manually, because its
  subject is generated by Azure DevOps and cannot be known beforehand.
- At run time the pipeline presents a token from Azure DevOps. Entra checks it
  against the credential and issues an access token for the role assignments.

## What broke, and how I fixed it
1. **Subject unknown until the wizard generates it.** The credential needs the
   subject, but the subject exists only while the service connection wizard is
   open. The wizard was left open while the subject was copied into Terraform,
   applied from the merged main branch, and then the wizard was completed.
2. **Manual step.** The service connection itself is not managed as code. The
   decision and its limits are recorded in ADR 0003.
3. **Sufficiency of the roles.** Whether Website Contributor and Reader were
   enough for a deployment to a web app with private access was not known in
   advance. The first pipeline run on 2 November completed the deployment and
   the configuration update with these roles.

## Trade-offs
- The subject is tied to one service connection. If the connection is recreated,
  its subject changes, and the federated credential must be updated.
- Roles are assigned at the resource group, which is broader than the web app.
  The web app does not exist between sessions, since the workload stack is
  rebuilt each time, so a web-app scope would need to be reapplied each time.
- The application registration is in the shared stack, which is applied
  manually, so changes to the identity are not gated by a pipeline.

## Questions this answers in an interview
- What is workload identity federation, and why is it better than a secret?
- What do the issuer, subject and audience each prove?
- How do you separate deployment permissions from infrastructure permissions?
- What would you change if the service connection were recreated?
- What is the minimum role set for deploying to App Service?

## One-line pitch
The pipeline deploys with a short-lived federated token, no stored secret, and
permissions limited to publishing to one resource group.
